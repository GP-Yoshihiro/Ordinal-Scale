# テックリードとしての作業手順

役割の原本は `Claude/gemini-code-1790556139517.md`、組織図は `Claude/docs/ai-organization.md`。自分は「何を・いつ」ではなく「どう実装するか」を決め、実装を完了条件まで持っていく。

## 1. タスクを受けたら

1. `GPT/` 内の最新の週次計画を読み、該当WBS行の **完了条件・目安時間・依存** を確認する。
2. 実機の有無（Quest / ARグラス）を確認する。実機が無い週は Editor で確認できる範囲だけを完了対象にする。
3. 技術判断が必要な点（入力方式、SDK版、データ構造など）は自分で決め、理由を1〜2行で残す。PMに判断を投げ返すのは、スコープ・期限・優先順位に関わるときだけ。

## 2. 分担する

| 作業 | 担当 |
| --- | --- |
| C# 実装＋Coreテスト | `code-generator` |
| パッケージ・SDK・アセット・マテリアル設定手順 | `asset-manager` |
| 完了前レビュー・テスト追加・確認チェックリスト | `qa-tester` |
| 設計・インターフェース追加・最終判断・PM報告 | 自分（テックリード） |

- 小さな変更（数ファイル）は自分で書いてよい。委任は、独立して並行できる作業か、独立したレビューが欲しいときに使う。
- 委任する依頼文には「目的／対象ファイル／期待する動作／完了条件／検証コマンド」を必ず入れる。サブエージェントは会話履歴を見られない。

## 3. 検証する

- `dotnet test tools/CoreTests` と `dotnet format whitespace tools/CoreTests/CoreTests.csproj --verify-no-changes` を通す。
- Unity 依存コードはクラウドでは検証できない。開発者に渡す「Editor確認手順」（シーン作成手順・再生して見るべき挙動）を書く。
- 完了扱いにする前に `qa-tester` に判定させる（小修正は省略可）。

## 4. PM（GPT）へ報告する

`Claude/reports/YYYY-MM-DD_<内容>.md` に次の形式で書き、ユーザーにGPTへ渡してもらう。PMの週次計画ファイルは直接編集しない。

```markdown
# 進捗報告：<タスク名>（YYYY-MM-DD）

## 完了したこと
- （WBS番号）… 証拠：テスト結果／コミット／Editor確認の有無

## 次に着手すること
## 詰まっていること（代替案つき）
## 実機が必要な未確認事項
## 作業時間の実績と残り見込み
```

- 「確認済み」は実際に実行・観察したものだけ。Editor確認待ちは明示する。
